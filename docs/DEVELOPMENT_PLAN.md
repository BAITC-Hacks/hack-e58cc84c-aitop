# План разработки FAQ-бота командой из трёх человек

## Цель первой версии

Сделать терминального бота, который читает пять пар «вопрос — ответ» из
`faq.txt`, находит ответ по ключевым словам и выводит «не знаю», если вопрос
не похож ни на один известный.

Для первой версии используем Python 3 и только стандартную библиотеку. Это
позволит запустить проект одной командой и не тратить время на зависимости.

## Согласованный интерфейс модулей

До начала параллельной работы команда фиксирует два контракта:

- `load_faq(path: str) -> list[dict]` загружает вопросы, ответы и ключевые слова;
- `find_answer(user_text: str, entries: list[dict]) -> str | None` возвращает
  лучший ответ или `None`.

CLI вызывает эти функции, но не реализует поиск самостоятельно. Формат одного
блока в `faq.txt`:

```text
question: Во сколько начинается репетиция?
keywords: время, начало, начинается, когда
answer: Репетиция начинается в 18:00.
```

Блоки отделяются пустой строкой. Изменение этого контракта сначала обсуждается
командой, затем оформляется отдельным маленьким PR.

## Разделение работы

| Участник | Задача | Свои файлы | Результат |
|---|---|---|---|
| 1 — CLI | Диалог в терминале, команды выхода, обработка ошибок чтения файла | `main.py` | Бот запускается командой `python main.py` и ведёт диалог |
| 2 — поиск | Нормализация текста, подсчёт совпавших ключевых слов, порог «не знаю» | `matcher.py` | Чистые функции поиска без ввода/вывода |
| 3 — данные и качество | Пять FAQ-блоков, тесты поиска, инструкция запуска и описание результата | `faq.txt`, `tests/`, `README.md` | Реальные данные, автоматическая проверка и понятная сдача |

`README.md` сейчас содержит постановку задачи и имеет локальные изменения.
Поэтому до назначения участника 3 никто другой его не редактирует.

## Порядок работы

1. Вместе подтвердить тексты пяти ответов, контракт функций и формат
   `faq.txt` (до 10 минут).
2. Каждый создаёт свою ветку от свежей `main` и работает только в закреплённых
   файлах.
3. Участник 2 первым публикует сигнатуры функций и реализацию `matcher.py`.
4. Участники 1 и 3 подключают модуль и тестируют его через зафиксированный
   контракт.
5. PR сливаются в порядке: поиск → данные и тесты → CLI → финальная
   документация.
6. После каждого слияния автор следующего PR обновляет ветку через rebase и
   повторно запускает проверки.

## Критерии готовности

- В `faq.txt` ровно пять содержательных пар по темам: время, команда, трек,
  сдача и призы.
- Регистр, пунктуация и лишние пробелы не мешают распознаванию.
- Для известной темы выводится корректный ответ.
- Для несвязанного вопроса выводится «не знаю».
- Пустой ввод не завершает программу с ошибкой.
- Команда выхода завершает диалог.
- Все тесты проходят на чистом клоне, а README содержит команду запуска и
  краткий итог.

## Минимальная проверка перед сдачей

```powershell
python -m unittest discover -s tests
python main.py
git status --short
```

В последней команде не должно быть случайных временных файлов.
